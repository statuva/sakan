# Sakan Codebase and Q&A Guide

> Scope: current `main` implementation at the first codebase-cleanup checkpoint. This guide explains what the code does today, how the parts connect, and what is still planned. It is written for technical review and competition Q&A.

## 1. Thirty-second explanation

Sakan is a Flutter application backed by Firebase Authentication and Cloud Firestore. A signed-in user belongs to a family, configures recurring traditions and one-time family moments, records personal availability, and sees shared family information through Calendar, Moments, Profile, and setup flows. The code uses repository interfaces to separate Flutter screens from Firebase implementations. Current Calendar recommendations are rule-based and grounded in stored dates, rhythms, participants, and availability; an external generative-AI backend is not connected yet.

## 2. Current implementation status

### Implemented and connected

- Email/password sign-up, sign-in, password reset, and authentication routing.
- Family creation, invitation codes, join-by-code, and role-aware membership.
- Four-step Family Setup with members, traditions, configuration, and review.
- Firestore models for users, families, members, moments, rhythms, schedules, availability, care actions, memories, and Hub records.
- Personal profile, preferences, notification settings, privacy settings, and family settings persistence.
- Private recurring schedules plus label-free shared availability records.
- Family Moments creation/editing and Firestore-backed Calendar views.
- Care Action and Memory repository foundations.
- Role-aware controls for admin, adult, and child members.

### Present but not complete

- Home is a placeholder screen.
- Digital Twin is a placeholder screen.
- Calendar recommendations are deterministic/rule-based, not generated by an external AI model.
- Memory reading/details exist; the full photo-upload creation flow is not complete.
- Hub Settings is currently a UI/demo flow; NFC scanning is not connected.
- Care Actions can be stored, but scheduled operating-system notifications are not connected.
- Offline banner and demo-data infrastructure exist, but a full offline synchronization strategy is not implemented.

## 3. Architecture at a glance

```text
main.dart
  -> Firebase.initializeApp()
  -> SakanApp
       -> MaterialApp.router
       -> AppTheme
       -> appRouter
            -> authentication/setup routes
            -> AppShell
                 -> Home
                 -> Digital Twin
                 -> Profile
                 -> Calendar

Presentation screens
  -> AppDependencies
       -> repository/service instances
            -> Firebase implementations
                 -> Firebase Auth / Firestore

Firestore documents
  -> model.fromMap()
  -> typed Dart objects
  -> UI

User edits
  -> repository method
  -> model.toMap() / explicit update map
  -> Firestore
  -> snapshot stream
  -> UI refresh
```

## 4. Why the code is divided this way

| Layer | Responsibility | Examples |
|---|---|---|
| App/bootstrap | Starts Firebase, theme, routing, and global dependencies | `main.dart`, `app/`, `routes/` |
| Core | Shared visual constants and environment flags | `core/theme/`, `core/config/` |
| Feature presentation | Screens and feature-specific widgets | `features/*/presentation/` |
| Feature data | Firebase implementations for a feature | `features/*/data/` |
| Models | Typed representation of Firestore data | `shared/models/` |
| Repository interfaces | Contracts used by presentation code | `shared/repositories/` |
| Services | Cross-feature logic and context resolution | `shared/services/` |
| Shared widgets | Reusable buttons, cards, chips, and feedback states | `shared/widgets/` |

The main benefit is replaceability: a screen depends on a repository contract rather than embedding every Firestore path and query inside the UI.

## 5. Core concepts you must be able to distinguish

### AppUser versus Member

- `AppUser` represents the account-level record under `users/{uid}`.
- `Member` represents that account inside a particular family under `families/{familyId}/members/{uid}`.
- Account data includes email and current family selection.
- Member data includes family role, relationship, age group, preferences, and availability.

### FamilyRole versus FamilyRelationship

- `FamilyRole` controls authorization: admin, adult, or child.
- `FamilyRelationship` describes family context: parent, child, grandparent, sibling, guardian, relative, or other.
- Relationship must never be used as a substitute for permission checks.

### FamilyMoment versus MomentInstance

- `FamilyMoment` is the definition: “Friday Lunch” or “Ali’s Graduation.”
- `MomentInstance` is one occurrence of that definition, including scheduled/start/end times and participation evidence.
- The current Calendar works mainly with `FamilyMoment`; session execution will use `MomentInstance` more heavily later.

### FamilyMoment versus RhythmRecord

- A recurring `FamilyMoment` stores title, category, expected participants, date/time, importance, and recurrence interval.
- `RhythmRecord` stores the measured state of that recurring moment: last occurrence, current gap, occurrence count, status, and confidence.
- One-time moments do not require a RhythmRecord.

### ScheduleBlock versus AvailabilityBlock

- `ScheduleBlock` is private to its owner and may include a label such as School or Work.
- `AvailabilityBlock` is a family-level, label-free busy interval used by Calendar calculations.
- The two records are written together so the Calendar can use availability without exposing private labels.

### Deterministic insight versus external AI

- The current `CalendarInsightService` ranks facts already present in Sakan: upcoming moments, rhythm status, importance, participants, and shared availability.
- It does not call an external LLM.
- Future AI should explain verified facts and propose actions; it should not invent family state or infer emotions.

## 6. Startup and navigation flow

```text
App launch
  -> StartupScreen
       -> no Firebase user: Sign In
       -> signed in, no current family: Family Access
       -> family setup incomplete: Family Setup
       -> setup complete: AppShell / Home
```

The bottom navigation is owned by `AppShell`, not by individual features. Auth and setup pages are outside the shell. The shell uses an indexed `StatefulShellRoute`, preserving the state of each main tab when switching tabs.

## 8. Important end-to-end flows

### Create family

```text
CreateFamilyScreen
 -> FamilyAccessRepository.createFamily()
 -> Firestore batch:
      families/{familyId}
      families/{familyId}/members/{creatorUid}
      invitations/{code}
      users/{creatorUid} currentFamilyId/familyIds
 -> FamilyCreatedScreen
 -> FamilySetupScreen
```

### Join family

```text
JoinFamilyScreen
 -> load invitations/{normalizedCode}
 -> validate active + expiry + requested role
 -> create families/{familyId}/members/{uid}
 -> update users/{uid}.currentFamilyId/familyIds
 -> wait for admin to finish setup
```

### Complete family setup

```text
FamilySetupScreen
 -> local RhythmSetupDraft list
 -> FamilySetupRepository.completeSetup()
 -> Firestore batch creates:
      moments/{momentId}
      rhythms/{momentId}
      family.setupComplete = true
 -> Startup/Home routing updates for all members
```

### Save personal schedule

```text
ScheduleEditorScreen
 -> ScheduleRepository
 -> one atomic batch writes:
      member-private scheduleBlocks/{blockId}
      family-level availabilityBlocks/{memberId_blockId}
 -> Calendar reads only label-free AvailabilityBlock records
```

### Add or edit recurring moment

```text
MomentFormScreen
 -> CalendarRepository.saveMoment()
 -> Firestore transaction writes FamilyMoment
 -> recurring: create/update matching RhythmRecord
 -> changed to one-time: remove obsolete RhythmRecord
 -> snapshot streams refresh Moments and Calendar
```

### Calendar recommendation

```text
Calendar streams Moments + Rhythms + Availability + Members
 -> CalendarInsightService ranks verified facts
 -> recommendation card/dialog
 -> user chooses Schedule Reminder
 -> CareActionRepository persists assigned action
```

No external model is currently required for this path. Future AI should receive the structured recommendation context and improve wording/actions while preserving the deterministic fallback.

## 10. Security model

- Authentication identifies the caller through `request.auth.uid`.
- Membership is proven by `families/{familyId}/members/{uid}`.
- Admin/adult/child authorization uses `Member.role`, not relationship.
- A joining user may read only the invitation and their own prospective member document.
- Personal profile and schedule writes must be restricted to the signed-in member’s approved fields.
- Family name, member administration, and Hub operations are admin-only.
- Calendar and Moments data are family-scoped.
- Flutter visibility is convenience; Firestore Security Rules are the actual enforcement boundary.

## 11. Privacy design decisions

- Private schedule labels stay under each member’s schedule subcollection.
- Shared Calendar logic reads label-free availability blocks.
- Sakan stores explicit role/relationship/preferences rather than inferring identity.
- The product does not claim to diagnose emotions, mental health, or relationship quality.
- NFC should verify intentional participation, not prove emotional connection.
- Any future AI should receive the minimum structured family context needed for the selected task.

## 12. Error, loading, and state handling

- Long-running screens expose loading and error states using shared feedback widgets.
- Firestore snapshot streams refresh UI after server changes.
- Forms validate required fields before repository calls.
- Repository methods throw on invalid ownership/state and let presentation convert failures to user-safe messages.
- `mounted` checks prevent UI updates after a screen is disposed.

## 13. Honest answers to likely Q&A questions

### “What is the novel contribution?”

Sakan combines a family-activity graph, recurring rhythm records, shared availability, meaningful one-time moments, and physical participation evidence into one family-specific state model. The defensible value comes from structured longitudinal family data, not from a generic chatbot.

### “Is the Digital Twin already complete?”

No. The data foundation is present—members, moments, rhythms, participation, availability, care actions, and memories—but the visible Digital Twin graph and simulation page remain a placeholder. That distinction should be stated clearly.

### “Is the AI currently live?”

No external generative model is connected in the current branch. Calendar insights are rule-based and inspect verified Firestore data. The planned AI layer will explain and organize those facts through a protected backend, with the rule-based engine remaining as fallback.

### “Why not call ChatGPT directly from Flutter?”

API secrets must not be shipped in the client. The planned flow is Flutter -> protected Firebase function -> AI provider -> validated structured response.

### “How do you avoid fake emotional scoring?”

Sakan measures observable system data: attendance evidence, recurrence gaps, completion state, participants, schedules, and user-selected importance. It does not label emotions or psychological health.

### “Why are there both users and members?”

A Firebase user is an account. A member is that account’s role and profile inside one family. Separating them supports family-scoped permissions and preferences.

### “Why duplicate schedule data as availability?”

It is deliberate privacy separation. The owner keeps labels such as School; the family Calendar receives only a busy interval and member ID.

### “How does cold start work?”

During setup, the family chooses recurring traditions, expected frequency, importance, participants, and dates. Sakan creates initial RhythmRecords with `stillLearning` and low confidence rather than pretending to have historical evidence.

### “How do you know someone attended an external event?”

Sakan does not claim passive detection for off-site events. External attendance must be user-confirmed. Home sessions can later use Hub check-in/out evidence.

### “What does the NFC Hub do?”

The planned Hub is a shared NFC ritual point. Members check in and out individually. It provides intentional participation evidence; it does not measure emotional connection. NFC implementation is not yet connected in the current code.

### “How are recommendations produced?”

Today, the Calendar insight service ranks actual moment urgency, rhythm drift, importance, participant data, and shared availability. Future AI may turn that structured evidence into a clearer action plan, but it will not determine the underlying facts.

### “How are permissions enforced?”

The UI hides unauthorized actions, but Firestore Security Rules independently verify authentication, membership, ownership, and role before allowing writes.

### “What happens if AI is unavailable?”

The deterministic insight service remains the fallback. Core Calendar, Moments, setup, schedules, and Firestore data do not depend on an LLM response.

### “What remains before the final demo?”

The major remaining product work is Home, visible Digital Twin, memory creation/upload, NFC, real notification delivery, external AI backend, fuller automated tests, and final visual polish.

## 14. Fast code walkthrough for judges

Use this order during a technical walkthrough:

1. `main.dart` — Firebase initialization.
2. `sakan_app.dart` — app theme and router.
3. `app_router.dart` + `app_shell.dart` — entry flow and four tabs.
4. `app_dependencies.dart` — repository/service composition.
5. `model_enums.dart`, `member.dart`, `family_moment.dart`, `rhythm_record.dart` — core domain.
6. `current_family_service.dart` — personalized family context.
7. One repository interface and its Firebase implementation.
8. `family_setup_screen.dart` — cold-start baseline.
9. `firebase_schedule_repository.dart` — private schedule/shared availability privacy pattern.
10. `calendar_insight_service.dart` — deterministic recommendation layer.
11. Firestore Security Rules — server-side authorization.
